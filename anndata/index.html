Querying AnnData stores¶

AnnData is a file format of the scverse ecosystem for annotated data matrices. Its axes are observations (obs) and variables (var), not necessarily cells and genes. This page uses a cell-by-gene example to query a store that AnnData.write_zarr() wrote: annotations (obs, var), the expression matrix (X), layers, embeddings (obsm) and pairwise matrices (obsp, varp).

The examples use the small test store in this repository. Run make generate_fixtures to create it. The store has 20 cells, named cell_0 to cell_19, and 8 genes, named gene_0 to gene_7.

When to use SQL instead of loading an AnnData object¶

Use anndata.read_zarr when you want an AnnData object for slicing, analysis, or plotting in Python. Use duckdb-zarr when the result you need is a table: counts by annotation, expression summaries, or joins to sample metadata in CSV, Parquet, or another DuckDB table. You can query the store from SQL without first constructing an AnnData object. This is a relational view of the data, not a replacement for AnnData's analysis APIs or a full round-trip representation of the object.

  • Start with read_zarr_tables to discover the available tables.
  • Use read_zarr with table_name := and, for child groups, group_path := for a one-off query. It decodes annotations and uses observation and variable names as coordinates, so you can join obs, var, and X by name.
  • Use read_zarr_views when several queries should share stable table names. Run the returned SQL to create views; the views still read the Zarr store, rather than copying it into DuckDB.
  • Use array_path := for a single array or encoded element, including arrays under uns, or to inspect encoding components. This lower-level route uses integer positions instead of observation and variable names; prefer the tables for annotation joins.

Sparse tables omit unstored zeros, so SQL aggregates need care: see Sparse matrices omit zeros. See Limits before substituting SQL reads for an AnnData workflow.

How a store maps to tables¶

The extension reads an AnnData store as a tree of tables. Each Zarr group is a DuckDB schema, and each set of variables with the same dimensions in a group is one table. The root group is the schema main. The design is in docs/design.md, decisions 8 and 9.

Element Dimensions Table
X obs, var main.obs_var
obs columns obs main.obs
var columns var main.var
layers/* obs, var layers.obs_var
obsm/<k> obs, <k>_component obsm.obs_<k>_component
varm/<k> var, <k>_component varm.var_<k>_component
obsp/* obs_i, obs_j obsp.obs_i_obs_j
varp/* var_i, var_j varp.var_i_var_j
raw/X obs, raw_var raw.obs_raw_var
raw/var columns raw_var raw.raw_var

The obs column holds the cell name (obs_names in AnnData) and the var column holds the gene name (var_names). Every table has these names, so you can filter and join any table by name. Both axes of obsp show cell names, and both axes of varp show gene names. The <k>_component column of an obsm table is the component number, from 0.

If a data frame has a column with the same name as its axis, for example an obs column called obs, that column keeps its path in the store as its name, "obs/obs". Otherwise it would have the same name as the column of cell names.

The extension decodes AnnData's encodings:

  • A categorical column with string categories reads as a DuckDB ENUM of its categories. A categorical with other categories (for example integers) reads as the type of its categories. A missing value is NULL.
  • A nullable column (nullable-integer, nullable-boolean, nullable-string-array) reads as its values, with NULL where the mask is set.
  • A sparse matrix (csr_matrix or csc_matrix) reads as one row for each stored entry. See Sparse matrices omit zeros.

The extension does not read uns. Read its arrays one at a time with array_path= (see Read one array).

List the tables¶

read_zarr_tables gives one row for each table. group_path is the Zarr group, schema_name is the DuckDB schema for that group, and table_name is the table name.

SELECT group_path, schema_name, table_name, dims
FROM read_zarr_tables('test/fixtures/anndata/pbmc_like.zarr');

/        main    obs                   [obs]
/        main    obs_var               [obs, var]
/        main    var                   [var]
/layers  layers  obs_var               [obs, var]
/obsm    obsm    obs_X_umap_component  [obs, X_umap_component]
/obsp    obsp    obs_i_obs_j           [obs_i, obs_j]
/varp    varp    var_i_var_j           [var_i, var_j]

Read a table¶

read_zarr reads the root group. The root has three tables, so use table_name := to select one by the name read_zarr_tables gives it (dims := with its dimensions works too). Use group_path := to read another group.

-- Cell annotations: one row for each cell
SELECT obs, cell_type, donor, n_genes
FROM read_zarr('test/fixtures/anndata/pbmc_like.zarr', table_name := 'obs');

-- Gene annotations: one row for each gene
SELECT var, gene_symbol, mean_expr
FROM read_zarr('test/fixtures/anndata/pbmc_like.zarr', table_name := 'var');

-- The expression matrix: one row for each stored entry
SELECT obs, var, X
FROM read_zarr('test/fixtures/anndata/pbmc_like.zarr', table_name := 'obs_var');

-- Two layers of one cell, by name
SELECT var, spliced, unspliced
FROM read_zarr('test/fixtures/anndata/pbmc_like.zarr', group_path := 'layers')
WHERE obs = 'cell_0';

In this store, cell_4 has no cell type, so cell_type is NULL for cell_4. gene_6 has no symbol, so gene_symbol is NULL for gene_6.

"group" := is the same parameter as group_path :=. GROUP is a keyword in DuckDB, so the quotes are necessary.

Mount the store as a database¶

Views give each table a stable name, so queries do not repeat read_zarr. read_zarr_views returns the SQL statements that mount the store, one statement in each row. Run the statements in order and stop on the first error. They attach a new in-memory database, create one schema for each group, and create one view for each table. The database alias must not already exist; the first statement rejects it rather than replacing its views.

SELECT sql FROM read_zarr_views('test/fixtures/anndata/pbmc_like.zarr', 'pbmc');

ATTACH ':memory:' AS "pbmc";
CREATE OR REPLACE VIEW "pbmc"."main"."obs" AS SELECT * FROM read_zarr('test/fixtures/anndata/pbmc_like.zarr', table_name := 'obs');
CREATE OR REPLACE VIEW "pbmc"."main"."obs_var" AS SELECT * FROM read_zarr('test/fixtures/anndata/pbmc_like.zarr', table_name := 'obs_var');
CREATE OR REPLACE VIEW "pbmc"."main"."var" AS SELECT * FROM read_zarr('test/fixtures/anndata/pbmc_like.zarr', table_name := 'var');
CREATE SCHEMA IF NOT EXISTS "pbmc"."layers";
CREATE OR REPLACE VIEW "pbmc"."layers"."obs_var" AS SELECT * FROM read_zarr('test/fixtures/anndata/pbmc_like.zarr', group_path := 'layers', table_name := 'obs_var');
...

In Python, run each row:

for (sql,) in con.sql("SELECT sql FROM read_zarr_views('pbmc_like.zarr', 'pbmc')").fetchall():
    con.execute(sql)

In the DuckDB CLI, write the rows to a file, then read the file:

.bail on
.mode list
.headers off
.once mount.sql
SELECT sql FROM read_zarr_views('pbmc_like.zarr', 'pbmc');
.read mount.sql

A table in main needs no schema name: pbmc.obs is pbmc.main.obs. The examples in the rest of this page use these views.

To give a view a different name, use view_names :=. A key is a table name from read_zarr_tables. For a table that is not in the root group, the key starts with the group path:

SELECT sql FROM read_zarr_views('pbmc_like.zarr', 'pbmc',
  view_names := MAP {'obs_var': 'X', 'layers/obs_var': 'layers'});

The views read the store again for each query. If you run many queries, CREATE TABLE ... AS SELECT copies the data into DuckDB once.

Sparse matrices omit zeros¶

AnnData usually stores X as a sparse matrix. A table of sparse matrices has a row only where a matrix stores a value. A missing row means the value is 0. This store has 27 stored entries in a matrix of 160 cells, so the X table has 27 rows.

A matrix can store one position more than once if it was written without scipy's sum_duplicates(). That position gives one row, with the sum of the entries, as in scipy and anndata.

For this reason, AVG(X) over the X table is a mean over the stored entries only. To get a mean over cells, start from obs and use a LEFT JOIN. Each cell then has one row, and COALESCE gives 0 to the cells that have no entry:

-- Mean expression of Cd4 in each cell type
SELECT o.cell_type, AVG(COALESCE(x.X, 0)) AS mean_cd4
FROM pbmc.obs o
LEFT JOIN (
  SELECT x.obs, x.X
  FROM pbmc.obs_var x JOIN pbmc.var v USING (var)
  WHERE v.gene_symbol = 'Cd4'
) x USING (obs)
GROUP BY o.cell_type;

B cell   17.666667
NK cell   9.333333
T cell   23.142857
NULL      0.000000

When the gene names are the gene symbols, the inner query is not necessary: LEFT JOIN pbmc.obs_var x ON x.obs = o.obs AND x.var = 'CD4'.

If a group has two or more sparse matrices with the same dimensions, they share one table. The table has a row for each position that at least one matrix stores. A matrix that has no value at that position reads as 0 in that row. In this store, layers/spliced stores 53 entries and layers/unspliced stores 80. The layers.obs_var table has 106 rows, because 27 positions are in both.

If a group has a sparse matrix and a dense array with the same dimensions, the table has a row for each cell. The sparse matrix reads as 0 where it stores no value. In this store, varp has a dense corr and a sparse corr_csc, so the varp.var_i_var_j table has 64 rows.

Embeddings and pairwise matrices¶

An obsm table has one row for each cell and component. Use FILTER or PIVOT to get one column for each component:

-- UMAP coordinates of each cell
SELECT u.obs,
       MAX(u.X_umap) FILTER (WHERE u.X_umap_component = 0) AS umap_1,
       MAX(u.X_umap) FILTER (WHERE u.X_umap_component = 1) AS umap_2
FROM read_zarr('test/fixtures/anndata/pbmc_like.zarr', group_path := 'obsm') u
GROUP BY u.obs;

An obsp table has one row for each stored pair of cells. For a neighbor graph, the neighbors of one cell are:

SELECT obs_j AS neighbor, connectivities
FROM read_zarr('test/fixtures/anndata/pbmc_like.zarr', group_path := 'obsp')
WHERE obs_i = 'cell_3';

Cell names must be unique¶

Joins on obs and var compare names. If two cells have the same name, a join matches each row of one cell to both cells, and the result has extra rows. anndata warns about duplicate names when it loads such a store. Make the names unique before you write the store, for example with adata.obs_names_make_unique() and adata.var_names_make_unique().

Read one array¶

array_path := reads one array and ignores the group structure. Use it for uns, or to look at the arrays that hold an encoded column.

An AnnData element gets the same dimension names as in its table, but one array has no index to take names from, so its dimension columns hold integer positions. For example, array_path := 'obs/n_genes' gives the columns obs (0 to 19) and value. An array inside an encoded group has no AnnData dimensions. Its dimensions are dim_0, dim_1, and so on. For example, array_path := 'obs/cell_type/codes' gives the integer codes in the columns dim_0 and value, and the categories are not applied. Pass dims := to replace that placeholder with a more useful name for this query:

SELECT cell, value
FROM read_zarr('test/fixtures/anndata/pbmc_like.zarr',
  array_path := 'obs/cell_type/codes', dims := ['cell'])
ORDER BY cell;

The value is still the raw category code; it does not become a coordinate, and dims := cannot rename the already-named obs/var dimensions of an ordinary AnnData table read. See How duckdb-zarr works for the full rules.

read_zarr_metadata lists every array. The array_path_dims column gives the dimension names that array_path := uses for each array. With group_path :=, it lists the arrays of that group's tables: group_path := '/' gives the arrays of X and of the obs and var columns.

SELECT name, dtype, shape, array_path_dims
FROM read_zarr_metadata('test/fixtures/anndata/pbmc_like.zarr')
ORDER BY name;

array_path := also selects an encoded column on its own, decoded: a sparse matrix, a categorical or a nullable column. Like one array, its dimension columns hold integer positions. For example, array_path := 'X' gives the stored entries of a sparse X as obs, var and value, and read_zarr_metadata(store, array_path := 'X') lists the arrays it is made of. group_path := cannot name an encoded column, because it is not a group of tables.

SpatialData stores¶

This section covers the AnnData tables inside SpatialData stores and a join to a label image. It is not a comprehensive SpatialData tutorial and does not cover coordinate transformations or spatial analysis APIs. The tested example uses a small synthetic SpatialData-like store; it does not validate every SpatialData element or storage version.

A SpatialData store keeps each table as an AnnData object at tables/<name>. The extension reads any group with encoding-type: anndata as an AnnData object, so each table is a schema of its own: tables/cells has the tables obs, var and obs_var, and tables/cells/obsm has the embeddings, with the cell names of tables/cells.

The other elements of a SpatialData store are not AnnData:

Element Format Read it with
images/<name>, labels/<name> OME-Zarr read_zarr. Read one scale with array_path := 'labels/<name>/s0'.
points/<name> Parquet files in points.parquet/ read_parquet('store.zarr/points/<name>/points.parquet/*.parquet')
shapes/<name> GeoParquet file shapes.parquet read_parquet('store.zarr/shapes/<name>/shapes.parquet'). The geometry column is a DuckDB GEOMETRY.
tables/<name> AnnData read_zarr with group_path := 'tables/<name>'

A table's attributes name the element it annotates (region), the obs column that holds that element's name (region_key), and the obs column that holds the instance id (instance_key). Join the table to the element on the instance id:

  • In a label image, the pixel value is the instance id.
  • In points, the instance id is a column, usually instance_id.
  • In shapes, the instance id is the row's index. GeoPandas does not write a default index (0, 1, 2, ...), so use the row number: read_parquet(..., file_row_number := true) adds it as file_row_number.

The example store test/fixtures/anndata/spatialdata_like.zarr has a label image labels/cells and a table tables/cells that annotates it. This query gives the area in pixels of each cell:

SELECT o.instance_id, o.region, COUNT(*) AS area_px
FROM read_zarr('test/fixtures/anndata/spatialdata_like.zarr',
  array_path := 'labels/cells/s0') AS l
JOIN read_zarr('test/fixtures/anndata/spatialdata_like.zarr',
  group_path := 'tables/cells', table_name := 'obs') AS o
  ON l.value = o.instance_id
GROUP BY ALL
ORDER BY area_px DESC;

┌─────────────┬────────┬─────────┐
│ instance_id │ region │ area_px │
├─────────────┼────────┼─────────┤
│           2 │ cells  │       4 │
│           1 │ cells  │       3 │
│           3 │ cells  │       2 │
└─────────────┴────────┴─────────┘

read_zarr_views mounts the tables and labels of a SpatialData store, for example as sd."tables/cells".obs. It does not mount points or shapes, because they are not Zarr. Create views for them with read_parquet.

Limits¶

  • The extension uses this layout only in groups with encoding-type: anndata. An old store that has no encoding-type attributes reads only with array_path :=.
  • The extension does not read uns or awkward arrays. In a MuData store, the modalities (mod/<name>) read as AnnData objects, but the global obs and var do not.
  • Sparse matrices with the same dimensions and no dense array beside them share a table only if all are CSR or all are CSC. A table that mixes the two has no table_name in read_zarr_tables; read each matrix with array_path :=.
  • If two columns of one data frame differ only in case, or one has the name of its axis, they keep their paths as names ("obs/obs"), because DuckDB column names ignore case. A path that still collides gets a number ("obs/Obs_1").
  • Remote stores need consolidated metadata to list arrays. Without it, only array_path := works.
